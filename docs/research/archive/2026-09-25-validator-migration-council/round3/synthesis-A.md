### Q1. Must the agent push itself?

Variant B — external trusted delivery — for every mode that publishes: the agent ends with a local commit; validation runs; the launcher/orchestrator, the only holder of write-capable credentials, performs the allowed push. Variant A (agent pushes) is disfavoured even for approved publication: credentials would have to live in the agent's environment, recreating F-3P-1's precondition (FACT: the finding exists only where the process holds write-capable credentials, ODR §1). Variant C (hybrid) collapses into B for this project: the set of publishing task types is small (approved implementation delivery, release), and one trusted delivery layer is simpler, safer and more auditable than two push paths. Costs: one extra logged, retryable launcher step after validation — negligible latency, better failure recovery and auditability. INFERENCE; no contrary evidence in the corpus.

### Q2. Sandbox isolation per mode?

Level 0 (policy only, "do not push"): acceptable for nothing that also holds write credentials — F-3P-1 shows instruction-plus-config controls fall to one command (L3); acceptable only where credentials are already absent, where it is not the control doing the work. Level 1 (credential profile + config hygiene): sufficient for the current threat model (cooperative agents; injection-class content) — it removes the precondition instead of chasing transports. Level 2 (process/user isolation): justified when jobs execute untrusted code with stored credentials reachable, or if the owner admits the adversarial-agent class; not justified for today's research runs, which already isolate the tree (private clone per attempt, `launch.cjs:400-426`). Level 3 (VM / strong isolation): premature and excessive — no measured incident, high friction; revisit only on a threat-model change (owner decision).

### Q4. The role of `ls-remote` before/after

Secondary invariant, tripwire and audit evidence — never primary enforcement (ODR §1 already rejects it as a boundary). Scenarios: new ref — detected; force push — detected if compared per-ref; push+revert — the transient state escapes a before/after diff (FACT by construction; ODR §1 names it); tag push — detected; branch deletion — detected; webhook/CI side effects — NOT detected (not refs); a remote other than origin — detected only if the comparison enumerates a recorded remote list. Correct use: run it after every job in every mode, log the before/after ref sets as audit evidence, and treat a difference in a no-push mode as an incident invalidating the run — knowing it can miss a transient push or a side effect.

### Q5. Can the delivery policy be tiny?

Yes: a two-line task descriptor — `git: {mode: LOCAL_COMMIT}` or `git: {mode: BRANCH_PUSH, target: agent/<name>}`. Four modes (READ_ONLY, LOCAL_COMMIT, BRANCH_PUSH, RELEASE_PUSH) per L-GIT-01; no policy DSL — no variant in the matrix needs more expressiveness than mode + explicit target ref.

### Q6. How is the mode determined?

Procedure-derived, with owner-defined override at dispatch: research/council/audit frames default to READ_ONLY or LOCAL_COMMIT (both no-push; PROTO-DEC-0070 item 4 already forbids push for the research run); BRANCH_PUSH and RELEASE_PUSH come only from the task's authorisation. Agent-requested escalation widens authority and follows PROTO-DEC-0070 item 6 — to the owner/coordinator, never to the launcher. An automatic classifier is rejected: misclassification is silent, non-deterministic and unaccountable (HYPOTHESIS; the project already pays determinism for liveness elsewhere, `P-L3-004:217`).

### Q7. Default-deny?

Yes: a task that does not explicitly declare publication gets NO REMOTE MUTATION. Operational load is zero in the common case — derivation is procedural (Q6) and the research run already lives under exactly this default (0070 item 4); friction appears only for tasks that legitimately publish, which are rare and deserve the explicit descriptor.

### Q8. Successful acceptance test

A hostile suite, not one blocked push. No-push mode attempts: (1) direct `git push`; (2) `git -c url.<x>.insteadOf=<origin> push` (L3 bypass A); (3) an added alternate remote; (4) mutation of the clone's config (already SCOPE_STOP, `launch.cjs:434-435`); (5) ambient global config via `GIT_CONFIG_GLOBAL` (L3 bypass B); (6) tag push; (7) new-branch push; (8) force push; (9) the credential-helper path; (10) another git executable/path where applicable. Acceptance per attempt: exit ≠ 0 AND identical `ls-remote` before/after ref sets AND no credential material reachable in the executor env (assert `GH_TOKEN` unset, helper chain empty). Push-enabled mode additionally: the allowed target succeeds; a forbidden target is blocked; publication happens only after the validation stage (the delivery layer refuses a push request without a passed-validation token). Closure rule: F-3P-1 closes only when variants (2), (5) and (9) fail for lack of credentials even though git resolves a real URL — L3 remedy 1 plus the credential profile; recording the residual alone does not close it.

### Q9. The reverse hypothesis — is the finding too strict?

Required estimate: risk × probability × blast radius against implementation + maintenance + execution friction. Risk: an unreviewed or hostile-steered push to a shared remote is irreversible (FACT: "a push cannot be undone and leaves no artifact", L3 F-3P-1; pushed history is not rewritten, AGENTS.md §10). Probability: low for cooperative agents (the assumed mode, `P-L3-004:219`); non-trivial under injection — Study A reads untrusted external content by design (L3). Blast radius: publication of the checkout HEAD plus side effects (CI, webhooks) to arbitrary destinations — bounded but public and unrecallable. Cost of the recommended control (credential profile + descriptor + ls-remote audit): small — env sanitisation and one ref-set diff per job; no new infrastructure. Cost of Level 2-3 isolation: high — per-job Windows identities or containers on a launcher whose process-table query already costs 519 ms idle and seconds under load (M-13), plus an isolation layer to maintain. Verdict: the reverse hypothesis is REJECTED for the Level-1 control (friction far below the irreversibility risk) and ACCEPTED for Level 2-3 (the isolation architecture costs more than the current threat model justifies). F-3P-1 is real but small-scoped; the minimum mechanism closes it.

### Q10. Safety boundary vs workflow boundary

Both, as different layers. The workflow boundary (declared mode; when publication is allowed; the escalation path) governs legitimate delivery and must stay cheap and explicit (Q5/Q6). The security boundary (no write credentials + config hygiene in no-push modes) physically removes the capability where publication must not exist and must not depend on the agent's compliance. The workflow layer alone is the F-3P-1 status quo and is defeated (L3); the security layer alone would block legitimate delivery. The trusted delivery layer (Q1 variant B) is where they meet: the only component holding push capability, publishing only on a validated, in-mode request.

### Proposed resolution (input to the draft step)

Adopt the hybrid minimal architecture: task-declared git modes with default-deny (Q5-Q7); a credential-profile security boundary in every executor environment (Q2 Level 1; Q8); retention of the existing `insteadOf` rule as defence in depth with its `-c` residual honestly recorded in R-L3-004.9 (L3 remedy 1); `ls-remote` before/after as audit and tripwire (Q4); and a trusted delivery step in the launcher as the only publishing path (Q1 variant B; Q10).
