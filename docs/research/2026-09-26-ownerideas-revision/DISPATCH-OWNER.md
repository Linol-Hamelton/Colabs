`OwnerIdeas` не должен становиться вторым источником истины.

- описана в ядре;
- документирована;
- имеет актуальный canonical source;
- при необходимости покрыта тестами/валидацией;

то исходный исследовательский материал больше не должен продолжать жить как активный источник требований.

Принцип:

> **Реализовано, принято и канонически задокументировано → исходный источник должен быть очищен или удалён из активного корпуса.**

+

+

как шесть активных источников одной и той же истины.

После переноса решения в ядро canonical authority должен находиться в ядре.

Исходные материалы не должны создавать шум или конкурировать с актуальной документацией.

# 5. Что считать кандидатами на удаление

Помечать как **DELETE / ARCHIVE CANDIDATE**, если содержание:

- заменено более новым решением;
- отражено в canonical kernel documentation;
- отражено в accepted decision;
- описывает уже завершённое голосование;
- описывает уже закрытый consensus;
- является промежуточным research artifact завершённого решения;
- является старой сертификацией уже принятого и реализованного решения;
- противоречит более новому принятому решению;
- больше не имеет самостоятельной информационной ценности.

Важно:

> На этом этапе ничего автоматически не удалять.

Сначала только классификация и обоснование.

# 6. Что считать актуальным

Помечать как **KEEP / ACTIVE**, если идея:

- ещё не реализована;
- остаётся архитектурно актуальной;
- не имеет canonical replacement;
- описывает незакрытый системный пробел;
- содержит требования, отсутствующие в текущем ядре;
- особенно относится к уровням **L0–L3**;
- может существенно повлиять на архитектуру последующих стадий.

Для каждого такого пункта указать:

- где он должен жить;
- с каким слоем связан;
- что уже существует;
- чего ещё не хватает;
- требуется ли решение, исследование или непосредственная реализация.

# 7. Что считать темой отдельного исследования

Помечать как **RESEARCH CANDIDATE**, если идея:

- имеет несколько разумных архитектурных вариантов;
- требует внешних данных;
- требует benchmark;
- требует экспериментов;
- требует сравнительного тестирования;
- содержит существенные неопределённости;
- потенциально влияет сразу на несколько слоёв.

Не превращать такую идею сразу в implementation task.

Для каждого из пяти пакетов определить:

```text
ID
goal
scope
inputs
allowed paths
forbidden paths
dependencies
required outputs
acceptance criteria
validation commands
integration conditions
```

---

# Этап 6 — детерминированный пакет реализации

Claude готовит **детерминированный implementation prompt/package** для всех пяти исполнителей.

Промпт должен максимально исключать свободную интерпретацию там, где решение уже принято.

Каждый исполнитель получает:

- точную цель;
- точный scope;
- входные документы;
- разрешённые изменения;
- запрещённые изменения;
- обязательные проверки;
- ожидаемые артефакты;
- критерии DONE;
- правила Evidence;
- зависимости от других пакетов.

Задача исполнителя:

> реализовать принятое решение, а не заново проектировать его.

Если исполнитель обнаруживает противоречие, которое невозможно разрешить внутри утверждённой спецификации, он блокирует пакет и возвращает finding вместо самостоятельной смены архитектуры.

---

# Этап 7 — предварительная проверка DeepSeek

До массовой реализации **DeepSeek 4.1 Flash** проверяет:

- итоговую резолюцию Claude;
- пять implementation packages;
- их полноту;
- зависимости;
- отсутствие пересечений;
- acceptance criteria;
- возможность детерминированной проверки результата.

При наличии blocking findings:

```text
DeepSeek
→ Claude
→ исправление пакета
→ DeepSeek re-check
```

Только после этого пакеты считаются готовыми к исполнению.

---

# Этап 8 — параллельная реализация пятью исполнителями

Claude запускает **5 исполнителей** по подготовленным пакетам.

Пакеты должны исполняться параллельно там, где зависимости это позволяют.

Исполнители:

- не меняют утверждённую архитектуру;
- не расширяют scope;
- не принимают новые owner-level решения;
- реализуют свой bounded package;
- передают результат на проверку.

Состав моделей исполнителей определяется до старта этого этапа и после старта **не меняется до закрытия всей задачи**.

Effort каждого исполнителя также фиксируется до старта и далее не меняется.

---

# Этап 9 — DeepSeek проверяет полную реализацию

После завершения всех пяти пакетов:

**DeepSeek 4.1 Flash** проводит первый полный post-implementation review.

Проверяется:

- соответствие финальному плану;
- соответствие пяти пакетам;
- полнота реализации;
- интеграция между пакетами;
- регрессии;
- L0–L3 consistency;
- tests;
- validators;
- документация;
- отсутствие оставшихся duplicate sources of truth.

Если PASS:

```text
→ финальный цикл закрытия
```

Если найдены дефекты:

```text
DeepSeek
→ конкретный findings list
→ repair cycle
```

---

# Этап 10 — первый repair cycle: Gemini

Если после реализации DeepSeek обнаруживает дефекты, первый repair выполняет:

**Gemini 3.8 Flash**

Gemini получает:

- финальный план;
- implementation packages;
- фактический результат;
- findings DeepSeek.

Gemini исправляет только подтверждённые findings.

После исправления:

**Mistral** выполняет независимую проверку исправленного состояния.

---

# Этап 11 — Mistral verification

Старшая доступная **Mistral** проверяет:

- исправления Gemini;
- исходные findings DeepSeek;
- отсутствие новых регрессий;
- соответствие утверждённой архитектуре.

Если PASS:

```text
→ последний цикл закрытия
```

Если FAIL:

```text
→ findings фиксируются
→ последний цикл всё равно переходит к DeepSeek
```

---

# Этап 12 — последний цикл: DeepSeek → Claude

Финальный verification cycle всегда:

```text
DeepSeek
↓
Claude
↓
CLOSED
```

## DeepSeek

DeepSeek повторно проверяет весь итоговый candidate:

- первоначальные findings;
- repairs;
- замечания Mistral;
- tests;
- validators;
- integration;
- documentation;
- отсутствие unresolved blocking findings.

Он формирует финальный технический verdict.

## Claude

Claude получает:

- весь final candidate;
- final DeepSeek review;
- Mistral review;
- историю repair cycle;
- исходный утверждённый план.

Claude выполняет финальное закрытие.

Возможные состояния:

```text
CLOSED
```

или:

```text
NOT_CLOSED
```

`CLOSED` разрешён только если:

- все обязательные пакеты выполнены;
- все blocking findings закрыты;
- validators/tests прошли;
- документация соответствует реализации;
- удалённые/архивированные OwnerIdeas не оставили dangling references;
- актуальные идеи получили canonical destination;
- утверждённые research candidates зарегистрированы;
- отсутствует второй активный источник истины для уже реализованных решений.

# 20. Неподвижность моделей и effort

Это правило действует для всей задачи от начала Round 1 до `CLOSED`.

После назначения:

```text
Gemini 3.8 Flash
Claude Opus 5.5
DeepSeek 4.1 Flash
Senior Mistral
Kimi K2.7 Code HighSpeed
MiMo-V2.6-Pro
+ 5 implementation executors
```

их нельзя автоматически заменять другой моделью.

Также нельзя автоматически менять назначенный reasoning effort.

Причины:

- воспроизводимость;
- чистота сравнения;
- понятная provenance;
- отсутствие скрытого изменения качества между раундами;
- возможность корректно оценить работу каждого участника.

Если назначенная модель становится технически недоступна:

```text
BLOCKED
→ OWNER DECISION
```

а не автоматическая замена.

# 21. Принцип завершения

Ни одна промежуточная стадия не означает завершение всей задачи.

```text
individual review DONE
≠ synthesis DONE
≠ plan DONE
≠ implementation DONE
≠ task CLOSED
```

Полное завершение существует только после:

```text
FINAL DEEPSEEK REVIEW
+
FINAL CLAUDE RESOLUTION
=
CLOSED
```
```

Есть ещё один момент, который я специально сделал явным: **Gemini не удаляет ничего до резолюции Claude**, а DeepSeek не превращает несогласованные идеи напрямую в задачи. Сначала четыре независимых чтения → два независимых синтеза → Claude фиксирует границу истины → только потом физическая очистка и планирование.

Так сохраняется ваша исходная последовательность, но случайное удаление ещё не распознанной идеи становится практически невозможным.
