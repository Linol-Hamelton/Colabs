## 4. L8 — расширение доступа

`P-L8-001` (класс C, по M §6 «[Сошлись]»):
- Чтение никогда не запрещено. Объявленный набор — минимум.
- Расширение чтения записывается строкой `Read-widening: <paths> reason=<text>` и ничего не стоит.
  Для правки ядра чтение широкое по умолчанию.
- Правом на изменения распоряжается только владелец либо записанное делегирование с объёмом (кому,
  какой scope, до какой даты). Делегирование — артефакт L5.
- Сертификатор расширяет чтение за пределы diff и записывает причину (0049 п.1).
- Изменения вне репозитория делает один агент, с резервной копией и записью в обоих местах (0048 п.8).

## 5. L9 — код

`P-L9-001`: до правки прочитай код и `git status`; работай внутри задачи; никаких попутных
переименований (AGENTS §9); ветка для всего крупнее мелкой правки (`AGENTS.md:438`). Область правки берётся из `task-frame.scope`, запрещённые пути — из
`task-frame.forbidden`; исполняет `protocol-scope.cjs checkScope`. Защищённое множество читается из
манифеста (0046 п.3). Git: без коммита, тега и пуша без владельца; замораживающий коммит — только по
путям scope (P-L2-008). Кодировки: UTF-8 без BOM, LF, `.ps1` только ASCII — исполняет валидатор.

## 6. Компилятор пакетов `protocol-core.cjs compile-packet`

```
compile-packet --role <slot> --stage <stage> --frame <task-frame> [--client <c>]
  → .ai/runtime/packets/<scope>-<slot>-<hash>.md
  состав: L0-ROOT (full) + ROLE-<slot> (full) + записи, где roles явно называет slot, а stages —
          stage или any (full) + схемы из их inputs (full) + записи с roles: [all] и остальное
          (summary из CATALOG; запись all открывается целиком по своему триггеру)
          + task-frame + environment-manifest   (правило — procedure.schema.md §4; CA-S2)
  детерминизм: одинаковые входы → одинаковые байты и хеш (тест из внешнего синтеза E: два агента
               с одной ролью и задачей получают идентичный пакет)
  бюджет: > 40 000 B → выход 1 с перечнем крупнейших записей
```

**Доставка по клиентам** зависит от нативной загрузки инструкций. Это вопрос 5 из
`kernel-architecture/BRIEF.md`, порученный Copilot. ФАКТ: отчёт `copilot-client-loading.md` в
репозитории отсутствует. Без него компилятор доставляет пакет **вставкой в промпт-файл**, это
работает у всех клиентов. Нативная ленивая загрузка — отдельное испытание (S6-T04, В-22).

## 7. Миграция

1. **RULE-MAP** (этап 1, S1-T07) → у каждого атомарного правила `AGENTS.md`, `PROTOCOL.md`,
   `PAIRED-CYCLE.md`, `CLI-AGENTS.md` и `CLAUDE.md` есть дом-запись или причина вывода.
   Проверяет `protocol-ledger.cjs cover`.
2. `AGENTS.md` становится тонким загрузчиком: что это за репозиторий, где корень, как начать сессию,
   ссылки. Цель ≤ 1 500 токенов (сейчас ~5,3k, M §2). `CLAUDE.md` импортирует его, как раньше (DEC-0002).
3. `.ai/docs/*.md` становятся указателями на записи и уходят в архив после одного пакета без обращений.
4. Манифест: `.ai/core/**` в `managed`; новые скрипты в `managed` и в список тестов; схемы поставляются
   хостам, история сигналов — нет.
5. Валидатор: лимит корня, lint схемы, `check-links`, единственность дома (поиск пересказов по id
   правил), паритет PS→Node.
6. Версия протокола **2.0**. Объём v2.0 из 0039 п.3 (единый Node-валидатор с дифференциальной
   проверкой, вынос живости процесса в листовой модуль, разделение `protocol-handoff.cjs`) входит в
   пакет III-b как класс D. Хеши и форматы квитанций заморожены, не удалены.
7. Хост-проекты (VPN, Block-Puzzle на 1.9.0) обновляются в своих сессиях после выхода из программы (0039 п.2e).

Теневые сертификаторы (Mistral, Copilot) могут получать тот же пакет в любом из пяти пакетов. Их
вердикт записывается и сравнивается с итогом, но **никогда не засчитывается** в гейт (0047 п.4).
Скрипты пакета I-b пишет исполнитель (Claude) после S3-T13..T15 и до заморозки I-b; DeepSeek проверяет их
как этап. Перед кодом каждого пакета замораживается список интерфейсов: scope, поля пакета, грамматики,
первые токены вывода, коды выхода (R-25).

Для каждого пакета: заморозка одним коммитом по путям scope (с разрешения владельца), пакет кандидата,
`record --candidate` производителя, два сертификатора параллельно в своих worktree, не больше трёх
раундов (0047 п.5). При исчерпании — владельцу, а не четвёртый раунд.

## 10. Выход из программы

Перед выходом — **A/B/C-тест** по P-L0-007 (PROTO-DEC-0060 п.2): A — новое ядро, B — старое
(`4ded1be`), C — без ядра; две-три задачи одной моделью в клоне какого-нибудь репозитория.
Отчёт — в `docs/reviews/`.

Программа закрывается, когда:
1. Пакеты I-a, I-b, II, III-a и III-b сертифицированы, а владелец одобрил их блоками решений.
2. Выполнен критерий «стабилен и измерим» (CORE-ARCH-6 §7).
3. Сквозной пилот прошёл, его отчёт в `docs/reviews/`.
4. Исключение PROTO-DEC-0054 п.2 снято новым блоком. Заморозка возвращается в виде, который определит владелец.
5. Продуктовые пилоты (Block-Puzzle, VPN) возобновляются по замороженным целям и метрикам PLAN.

## 11. Граф зависимостей всей программы

```
 Этап 0 (CORE-ARCH-1) ──→ Этап 1 L0 ──LCC──→ Этап 2 L1 ──LCC──→ Этап 3 L2 (+ S3-T13..T15: предпосылки) ──LCC──→ ПАКЕТ I-a ──→ ПАКЕТ I-b
                                                                     │
                                            Этап 4 L3–L4 ──LCC──→ Этап 5 L5–L6 ──LCC──→ ПАКЕТ II
                                                                                         │
                                                             Этап 6 L7–L9 + компилятор ──→ ПАКЕТ III-a ──→ миграция ──→ ПАКЕТ III-b
                                                                                         │
                                                                   Сквозной пилот ──→ выход ──→ продукты
 Конвейер (пилот P-L2-009, только после В-7): этап N+1 проектируется, пока DeepSeek ревьюирует этап N;
 посадка — строго по порядку.
```

Оценка объёма: каждый этап — один-два сеанса исполнителя плюс один-два ревью; пакет — один-три раунда
сертификации. ГИП. без измерения. После этапа 1 фактическое время запишется в M-007 и заменит оценку.
