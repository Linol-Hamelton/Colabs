# CORE-ARCH-5 — Этап 4. Слои L3–L4: инструменты и опыт их применения

- Статус: **предложение**, этап 4 программы CORE-ARCH (PROTO-DEC-0054). Не решение.
- Дата: 2026-09-24. Исполнитель: Claude. Ревьюер: DeepSeek.
- Вход: пункты R-11..R-13, R-19; PROTO-DEC-0043, 0047 пп.6–7, 9, 11, 0049 пп.3, 5, 0050, 0051 п.4.
- Начинается после LCC слоя L2.

## 0. Цель и результат

**Цель.** Каждый клиент и каждый инструмент описан **измеренными** данными, а не памятью модели.
Агента запускает скрипт по этим данным. Зависшего будит сторож, и каждый новый режим отказа
попадает в профиль клиента, а не остаётся в журнале.

**Разделение слоёв** (тест из P-L0-001 шаг 2):
- **L3** — что инструмент умеет, как его вызвать, какие у него права и флаги (данные плюс процедуры вызова);
- **L4** — что показала практика: режимы отказа, заявленные производителем, но не подтверждённые
  эффекты, и незаявленные, которые мы нашли (M §5, «применение инструментов»).

**Результат** (`docs/core-arch/stage-4/`): `client-profile.schema.md`, `clients.json` (форма и
значения, измеренные на дату), спецификация `protocol-dispatch.cjs` со сторожем, `TOOL-*.md` для
скриптов ядра, `APP-<client>.md` для каждого клиента, политика разрешений, раздел про K5.

## 2. Реестр клиентов (R-13)

Дом: `.ai/core/L3-tools/clients.json` (CORE-ARCH-1 §3.3). Схема — объединение полей трёх синтезов:

| Поле | Содержание | Кто назвал |
|---|---|---|
| `client`, `provider`, `family` | имя клиента, провайдер, семейство моделей (для правила «одна модель — одна роль» и чередования, PROTO-DEC-0056) | X, CORE-ARCH-3 |
| `version`, `verified` | версия CLI и дата плюс источник (`--help`, `models`) | C, X, D |
| `executable`, `shim` | как запускать; `.cmd`-обёртки npm → `node <entry.js>` или проверенный адаптер | C, X |
| `argv` | массив-шаблон, **без shell-строк** | C, X |
| `env` | обязательное окружение (vibe: `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`) | C, D |
| `models`, `effort`, `tiers` | матрица кандидатов и уровни усилий, девять рангов T1–T9; строится только процедурой P-L3-002 (PROTO-DEC-0058) | X, D, владелец |
| `permission` | узкий профиль прав и флаги (0047 п.7, 0049 п.5) | все |
| `timeBound` | флаг и значение жёсткого лимита | C, D |
| `sessionIdFrom`, `resume` | откуда взять id сессии и шаблон возобновления | C, X, D |
| `artifacts` | пути транскрипта и потока для сторожа | C, X |
| `failureModes[]` | `{cause, countermeasure, signal}` — переходит в L4 как указатель | C, 0050 п.3 |
| `enforcement.noCommit` | чем исполняется запрет коммитов: `gate` / `hook` / `detect-only` / `none` | X (K5) |

Правила реестра:
- Неизвестная версия или способность → выход 2. Явно неподдерживаемое возобновление ведёт к ветке
  «FALLEN на первом простое» (0051 п.4), а не к угаданному флагу.
- Пути машины не попадают в поставку: шаблоны `~` и `<root>`, локальное переопределение — в
  `.ai/runtime/` (C S-claude-13).
- Установленные проекты получают **схему и пустой реестр**, а не значения этой рабочей станции (X).

Измеренные значения на 2026-09-24 (D S-deepseek-08, `--version` и `--help`; перепроверяются в S4-T02):

| codex | 0.154.0 | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` | `codex exec resume <uuid> "<line>"` |
| agy | 1.2.9 | `transcriptPath` из хука | ГИП.: `--conversation <id>`, проверить пробой |
| copilot | 1.0.88 | `--log-dir` + stdout | `-r/--resume`, `--session-id` |

## 3. Диспетчер `protocol-dispatch.cjs` (P-L2-006 исполняет его)

- Вход — файл задания `{participant, client, scope, slot, promptFile, report, root, tier}`.
- Промпт — файл в репозитории. Агенту передаётся одна ASCII-строка: `Read and follow the file <repo-relative path>` (0050 п.2).
- Перед запуском: `toplevel == root`; в промпте есть строка «Step 0»; версия клиента совпадает с
  реестром; ранг → модель и усилие из `tiers`; окружение из `env`.
- Запуск: исполняемый файл плюс argv, **без shell**. Если обёртка неизбежна — отдельный проверенный адаптер.
- Лог: запрошенные и **наблюдаемые** модель и усилие раздельно; ненаблюдаемое — `unknown`.
- Счётчики раздельны: перезапуск упавшего процесса — один (0050 п.2); пробуждения — три (0051 п.4).
  Повторный провал — владельцу, если только первый провал не был дефектом самого диспетчера,
  и этот дефект уже исправлен.
- Перед каждым шагом переход записывается в журнал состояния, чтобы перезапуск диспетчера не
  продублировал работу (X S-codex-06).
- Выходы: 0 — все готовы с отчётами; 1 — есть FALLEN или FAILED; 2 — неизвестная запись или аргумент.
- `launch-round2.cjs` уходит на пенсию при сертификации пакета II (C S-claude-13).

## 4. Сторож: пробудить, потом признать упавшим (R-11, R-12)

```
 каждые 30 с: собрать сигналы активности своей сессии
   (a) stdout диспетчера  (b) транскрипт по пути из реестра  (c) отчёт и журнал своей сессии
   (d) вторичный: CPU дерева процессов — продлевает окно ≤ 1 раза на пробуждение и только
       при растущем выводе дочернего процесса-теста
 300 с без прироста (a)-(c) → простой
   → проверить состояние корневой причины: EXHAUSTED → не будить, стоп
   → убедиться, что прежний процесс не останется вторым писателем
   → WAKE-n (n ≤ 3): возобновить ту же сессию по id строкой
     "Continue from your last journal checkpoint in <journal>. If your journal records EXHAUSTED
      for the current root cause, stop and report."
   → новое окно 300 с внутри общего жёсткого лимита
 после WAKE-3 без прогресса → taskkill /PID <pid> /T /F → FALLEN
   → запись: session id, checkout, метки времени, последний чекпойнт, размеры артефактов,
     история пробуждений, пути и хеши логов (без секретов) → сигнал типа fall
```

Разрешение R-12: CPU — вторичный сигнал с ограничением, так что занятый цикл не держит сессию
живой бесконечно (возражение X), а долгий набор тестов на 315 с не считается простоем (C, D).
Записи чужих сессий не сбрасывают таймер (X S-codex-05).

## 5. Разрешения и запрет коммитов (R-19, K5)

- Узкие права по умолчанию (0047 п.7). Полный обход — только в одноразовом worktree с разрешением
  владельца в журнале; для agy — за шлюзом `protocol-gate.cjs` (0049 п.5).
- **Обнаружение** — для всех клиентов: диспетчер сравнивает HEAD и refs до и после запуска. Любой
  сдвиг — нарушение плюс сигнал `procedure-gap` (C, D).
- **Предотвращение** — по профилю: `enforcement.noCommit` записывает, чем оно достигается.
  Кандидат: `.git/hooks/pre-commit`, который отказывает при `PROTOCOL_DISPATCHED=1` (C, В-17).
  X прав: это не граница безопасности против произвольной команды shell. Поэтому поле называет
  фактическую силу, и `none` у клиента с широкими правами — выход 2 при запуске, пока владелец
  не разрешит явно.
- Изменения вне репозитория (конфигурации клиентов) — один агент, резервная копия, запись в журнале
  и в папке изменения (0048 п.8).

## 6. Управление внешними инструментами (0047 п.11)

- По умолчанию запрещено: список проекта — потолок, класс задачи решает, что включить, сессия
  грузит лениво.
- Испытание любого MCP, скилла или коннектора — парное A/B на одном SHA в отдельных worktree, с
  токенами схем, частотой вызовов, долей откатов и повторными чтениями.
- Graph Memory, если владелец когда-нибудь захочет попробовать его как **продуктовый** инструмент,
  идёт по этому шаблону как продуктовое решение; для протокола он закрыт 0045 п.1.
- Налог схем MCP измеряется до включения; бюджет 0034 п.2 — 1 500 токенов.

## 7. L4: карточки опыта `APP-<client>.md`

Каждая карточка — запись по схеме, `type: application`, с тремя разделами:
1. **Измерено**: версия, дата, команда измерения, результат.
2. **Режимы отказа**: причина → контрмера → сигнал (зеркало `failureModes`; дом — карточка,
   реестр держит машинную часть).
3. **Заявлено против подтверждено**: что обещает документация, что мы подтвердили или опровергли
   (M §5: «исключаем необоснованно заявленные эффекты и находим незаявленные»).

Первые карточки: `APP-vibe` (UTF-8), `APP-agy` (разрешения в headless, рабочая папка, таймаут 0s),
`APP-codex` (налог MCP, `--ignore-user-config`), `APP-deepseek` (нет CLI; Kilo; контекст 163 840),
`APP-claude`, `APP-copilot` (`--allow-all-tools` плюс узкая рабочая папка).
