## 0. Цель и результат

**L5** — память каскада и интерфейс между ветками. Ветки обмениваются **артефактами**, а не правилами
друг друга (M §4). **L6** — потребитель L5: считает то, что меняет решения. Метрику, которая ни одного
решения не меняет, выбрасываем (0047 п.11).

**Результат** (`docs/core-arch/stage-5/`): `artifact.schema.md`, каталог артефактов, спецификации
`record --candidate`, локатора воспроизведения, `protocol-signals.cjs`, `protocol-journal.cjs`,
определения метрик M-001..M-011, критерий «протокол стабилен и измерим».

## 2. Evidence производителя, привязанное к кандидату (R-08, R-09) — критично, пакет I-b

Проект делается на этапе 3 (S3-T14), потому что без него нельзя сертифицировать пакет I (CA-14).
Здесь — дом записи в L5 и её место в каталоге.

Условие «чистого дерева» заменяется **равенством дайджеста кандидату**:

```
node .ai/bin/protocol-handoff.cjs record --owner <session> --candidate <sha>
  1. <sha> — полный 40-hex коммит; потомок Baseline, иначе выход 2
  2. git worktree add --detach <tmp> <sha>; валидатор и набор тестов там; worktree удаляется в finally
  3. дайджест кандидата — из git ls-tree -r <sha> (минус сессионные пути, как в snapshot)
  4. в журнал производителя в основном checkout: anchor: <sha>, candidate-digest, коды выхода, хеш записи
verify / gate-check: пересчитывают дайджест из объектов git → квитанция не устаревает,
                     когда другие пишут в checkout
```

- Правки: `protocol-handoff.cjs` `anchor` 62–88, `renderEvidence` 109–135, `record`/`verify` в
  `main` 676–850, `gateCheck` 934+ (C S-claude-08; номера на `4ded1be`).
- PowerShell вызывает ту же проверку в Node, второго парсера Evidence не будет (X S-codex-04).
  Паритет проверяется тестом.
- Метка dirty остаётся **честной**: если дерево грязное, это так и записано (X). Связь даёт
  дайджест, а не метка.
- Пакет кандидата (CORE-ARCH-4 §5) ссылается на это Evidence полем `Producer-Evidence`.

## 3. Локатор воспроизведения (R-10) — пакет I-b

Проект — этап 3 (S3-T15); здесь дом записи.

Структура по X S-codex-04, записанная в ячейке ledger одной строкой фиксированной грамматики:

```
repro ::= "repo:" path "; interp:" ("node"|"pwsh"|"bash") "; argv:" json_array "; exit:" int "; sha256:" hex64
        | "external:" location "; sha256:" hex64 "; sanction:" decision_id
        | "none"
```

- `path` — относительный путь без `..`, без абсолютных форм и UNC (0046 п.2), обычный файл внутри
  кандидата; sha256 совпадает; иначе выход 2. При разборе ничего не исполняется.
- `external` требует блока санкции, который называет это заимствование (0048 п.5). По умолчанию
  исполняется копия внутри репозитория с тем же хешем. Сеть в гейте запрещена.
- `none` допустим только для рекомендаций и никогда не доказывает FAIL или BLOCKED (spec §3).
- Разовая миграция: скрипты из `D:\Colabs-cert\{codex,codex2,codex3,claude2,claude3}\...` кладутся
  по путям, которые называют строки ledger, в коммит кандидата. Каждая строка перезапускается из
  общего checkout, результат — в журнал исполнителя (D S-deepseek-07). Исторические строки не переписываются.

## 4. Реестр сигналов (R-14)

Дом: `.ai/SIGNALS.md`, только дописывание, пишет только `protocol-signals.cjs add`:

```
Signal: <id> | <type> | <date> | <participant> | <evidence> | <cost> | <disposition> | rc=<root-cause|-> | batch=<id|->
id          ::= sig-YYYYMMDD-NNN
type        ::= procedure-gap | script-candidate | fall
cost        ::= attempts=<n> | minutes=<n> | owner=<n> | unknown   (через запятую, если несколько)
disposition ::= open | grouped:G-<n> | procedure:<id> | script:<path> | kept-by-assistant:<spec §1 condition> | rejected:<reason> | closed:<ref>
```

- Изменение — новая строка с тем же id, последняя побеждает (как в REGISTRY). Неразборная строка → выход 2.
- Каждая строка однозначно переводится в JSON (`protocol-signals.cjs export --json`). Так закрыт
  довод X о машинной надёжности без второго формата.
- Одна строка — одна запись `appendFileSync`. Группировка по корневой причине — под блокировкой.
  Атомарность дописывания на NTFS — ГИП.; тест с параллельными писателями обязателен (X, C).
- `plan --batch <id>` группирует открытые сигналы, показывает группы, открытые два пакета подряд
  (эскалация владельцу, 0051 п.2), и **один раз** импортирует строки `Signal:` из журналов по хешу.
- Сигнал — основной триггер P-L0-001: `procedure-gap` открывает шаг 1; `script-candidate` проходит
  тест четырёх условий (шаг 6).
- В установленные проекты история сигналов источника не переносится (X).
