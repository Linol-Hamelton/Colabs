## 2. Правило свода: «наибольшее одобрение совпавших гипотез»

Версия 0.3 (исправлено по CA-10 и CA-23). Каждая гипотеза получает отметку от каждого источника, который её
касался: ✔ поддерживает, ◐ частично, ✘ против, — не касался. Отложить вопрос до редизайна тоже значит
его коснуться: отметка ◐. Уровень определяется только отметками тех, кто касался:

| Уровень | Условие | Что следует |
|---|---|---|
| **полный** | все касавшиеся ✔ | основа программы |
| **с оговорками** | нет ✘, есть ✔ и есть ◐ | основа; каждая оговорка получает ответ в §3.3 или в записи ядра |
| **большинство** | есть ✘, но ✔ больше, чем ✘ | вариант большинства; меньшинство получает ответ в §3.3, критики отвечают отдельно |
| **расхождение** | ни одного ✔, или ✔ не больше, чем ✘ | черновик разрешает в §3.3 с обоснованием; окончательно решает владелец |
| **один источник** | касался один источник | класс C: испытание (CORE-ARCH-2 §3), если не отклонено |
| **отклонено** | противоречит действующему блоку решений; заменяет любой другой уровень | не берём |

Колонка «Следствие» отдельно отмечает: **решено** (уже есть блок решения), **класс C** (новая
процедура без практического опыта идёт через испытание, какой бы ни была поддержка), **основа**.
Голос не перевешивает воспроизведение (PROTO-DEC-0041 п.5): где спор решает ФАКТ, побеждает ФАКТ.

### 3.3 Как решены расхождения

Разрешает автор черновика. Критики могут оспорить любое разрешение.

- **R-01, синтаксис.** Принимаю «scope обязателен» по X. Причина — директива владельца: роль
  выдаётся под задачу (H-07), значит у каждой роли есть задача, и строки без scope не нужны.
  Форма: `- <participant> @ <scope>: <role>{, <role>}`. `<participant>` — идентификатор линии
  сессий, не бренд (CORE-ARCH-3 §4). Ответ на оговорку DeepSeek (критика, 3.3-R-01): id scope выпускает
  владелец или координатор в поле `scope-id` рамки задачи (CORE-ARCH-4 §4; поле `scope` там — пути правки); сессия привязывается к линии и
  scope строкой `Orientation:` (CORE-ARCH-3 §6), которую сверяет скрипт. Без рамки scope не существует — выход 2.
- **R-06, детали.** Принимаю все три дополнения. Они не конфликтуют: событие попытки X, запретный
  путь C, `OWNER-EXCEPTION` D. Порядок — в CORE-ARCH-4 §6. По оговорке DeepSeek: `OWNER-EXCEPTION`
  обязан нести id одобряющего блока, запрещает повтор и открывает запись аудита (иначе выход 2).
- **R-10, синтаксис.** Принимаю структуру X. PROTO-DEC-0050 п.2 запрещает собирать команду руками,
  а шаблон `:: <command>` — это та же ручная сборка.
- **R-12.** Принимаю CPU как **вторичный** сигнал. Он продлевает окно не больше одного раза на
  пробуждение и только при растущем выводе дочернего процесса-теста. Так учтено возражение X
  про занятый цикл. «Растущий вывод» по оговорке DeepSeek: число байт stdout или транскрипта
  дочернего процесса больше, чем в прошлом замере 30 с назад. У условия свой тест в S4-T04.
- **R-13, путь.** `.ai/core/L3-tools/clients.json`: реестр — данные слоя инструментов (CORE-ARCH-5).
- **R-14.** md строками по большинству, но грамматика строки однозначно переводится в JSON
  (CORE-ARCH-6 §4), поэтому довод X о машинной надёжности закрыт парсером с выходом 2.
- **R-15.** Отдельный документ сценария в слое L2 (`.ai/core/L2-procedures/scenarios/`).
- **R-16.** ФАКТ решает в пользу большинства: блок не править, в индексе показывать фактический
  статус с происхождением.
- **R-17.** Вычеркнуть команду и оставить строку со ссылкой на 0036. X прав в одном: политика
  необязательного дайджеста из 0034 остаётся как история, и вычеркнутое переносится в архив, а не удаляется.

## 4. Основа программы (полный консенсус и консенсус с оговорками)

Из матрицы следуют десять опор. Каждая глава CORE-ARCH опирается на них и не пересматривает их без
триггера из `REGISTRY.md`.

1. **Каскад слоёв L0–L9** (H-01, H-02): корень короткий, слои грузятся по роли и этапу.
2. **Процедура о процедурах в корне** (H-02, H-04): одна процедура пишет, проверяет и выводит из
   обращения все остальные.
3. **Сбой → процедура, сигнал → реестр** (H-04).
4. **Грамматика вместо прозы на машинных входах** (H-05, R-01..R-04).
5. **Одно правило — один дом** (H-06, R-18).
6. **Независимость сертификации неприкосновенна** (H-09, 0041).

## 5. Внешний синтез E: что берём и что нет

**Берём, как класс A или C по методу CORE-ARCH-2:**
- Шаблон «рамка задачи + манифест окружения». Закрывает класс сбоя agy (M §7).
- Шаблон кросс-агентной сертификации со сквозным чтением инструментов исполнителя. Совпадает с M §6.
- Шаблон эскалации со стоп-вопросом из пяти блоков. Становится формой правила «не найдено — стоп» (H-03).
- Frontmatter у процедур: `roles`, `stages`, `permissions_required`, `supersedes`, `deprecated`.
  Это основа схемы в `stage-1/procedure.schema.md`, расширенная полями доказательств и исполнения.
- Уровни exists/summary/full как **уровни загрузки** (прогрессивное раскрытие), а не права.

**Не берём:**
- Graph Memory как MCP-сервер, эмбеддинги, веб-интерфейс, наблюдатели файлов.
  Основание: PROTO-DEC-0045 п.1, 0034, 0036.
- Код на Python и вызовы `httpx` к `localhost:3000/api/...`. ФАКТ: `architecture.md` описывает
  MCP-инструменты, REST и WebSocket, но таких конечных точек не называет. Примеры в E не проверены.
  Стек репозитория — Node и PowerShell.
- Утверждение «access resolution 5 уровней лучше ваших 3». ФАКТ: в R есть только строка
  `access.ts # Access resolution (5-level chain) + API key lookup`, семантики уровней нет.
- «Совпадает с Colabs на 90 %» — число без измерения.

**Паттерны R, которые переносятся** (подробно — CORE-ARCH-2 §5):

| В R | Перенос в ядро |
|---|---|
| Пронумерованные слои с одной точкой входа и ссылкой «See X» | каждый слой — индексный файл, у каждой процедуры один дом |
| `*-types.ts` отдельно от поведения | схема процедуры отдельно от текста процедур |
| md + YAML frontmatter как зеркало и источник | процедуры — md-файлы с ограниченным frontmatter |
| Индекс, производный от источника (BM25) | детерминированный каталог, как `decisions-index` (Layer B) |
| Прокси-узлы между графами и уборка сирот | проверка ссылок между слоями: висячая ссылка — дефект (как `ledger cover`) |
| PromiseQueue: изменения последовательно, чтение свободно | один писатель через блокировку, чтение никогда не запрещено |
| Отдельная схема потока данных на каждую операцию | у каждого сценария граф этапов и артефакты передачи |

### 6.2 Цикл этапа (как с кодом)

```
Этап N:  черновик (исполнитель)
   → самопроверка и проверка согласованности слоёв (§6.3), запись в журнал
   → ревью-промпт в docs/reviews/, отчёт ревьюера (DeepSeek)
   → FAIL/BLOCKED: исправление, не больше 2 попыток на корневую причину (0046 п.4)
   → PASS/RECOMMENDATION: пакет владельцу
   → владелец одобряет, правит или отвергает → блок решения (если обязывает)
   → Этап N+1 начинается только после проверки согласованности слоёв
```

Правило владельца «сдал на ревью и не ждёт» (H-19) — пилот класса C. Он **не применяется**, пока
владелец не ответит на В-7 (исправлено по CA-17). После одобрения: следующий этап можно
**проектировать**, пока ревьюер смотрит предыдущий, но **не посадить** в ядро (CORE-ARCH-4 §9).
Метрика — число переделок из-за FAIL предыдущего этапа.

### 6.3 Проверка согласованности слоёв (LCC)

Выполняется перед каждым следующим слоем, записывается в журнал исполнителя, проверяется ревьюером.

| # | Проверка | Как |
|---|---|---|
| LCC-1 | У каждого правила нового слоя один дом | каталог плюс поиск повторов (скрипт после этапа 6) |
| LCC-2 | Ссылки идут вверх или через артефакты; ссылка вниз — дефект, кроме ссылки вперёд на запись, которую пишет названный этап; при заморозке пакета все такие ссылки разрешены | индекс ссылок |
| LCC-3 | Нет конфликта с действующими решениями | обратный индекс `protocol-index.cjs` «путь → блоки» |
| LCC-4 | Каждый слот роли, на который ссылается процедура, есть в L1 | каталог |
| LCC-5 | Каждый инструмент из процедуры есть в L3 | каталог |
| LCC-6 | У каждого обратного ребра есть бюджет и выход | схема процедуры, поле `back_edges` |
| LCC-7 | Инварианты L0 (R-L0-03…R-L0-08) не нарушены ни одной процедурой | ручная проверка ревьюером, список инвариантов |
| LCC-8 | Бюджет контекста слоя соблюдён | подсчёт байтов, лимиты в CORE-ARCH-2 §6 |
| LCC-9 | Покрытие: каждое правило старых документов, относящееся к слою, перенесено или выведено с причиной | построчная карта правил (RULE-MAP); `cover` считает файлы и здесь не подходит (сигнал G1) |

Дом этих девяти проверок — P-L0-004 (`stage-1/P-L0-004-layer-consistency.md`); при расхождении верен он
(исправлено по CA-30, таблица собрана по CA-40).

### 6.4 Посадка и сертификация

Этапы 1–6 — это **проектирование со скелетом**. Черновики живут в `docs/core-arch/stage-N/`,
ядро не меняется. PROTO-DEC-0048 п.6 требует «чертежи и скелет до перестройки», а 0054 снимает запрет,
но не отменяет пользу этого порядка. Посадка в ядро идёт **пятью пакетами сертификации**; деление
решено заранее, а не при исчерпании (CA-14, CA-20; 0047 п.5 — не больше трёх раундов на пакет):

- **Пакет I-a** — записи L0–L2, схемы, `protocol-core.cjs lint/catalog/check-links`.
- **Пакет I-b** — критичные скрипты: роли и грамматика (R-01..R-03), сбор ledger (R-05), исчерпание
  (R-06, R-07), Evidence по кандидату и пакет (R-08, R-09), локатор (R-10). Их проект переносится
  с этапа 5 на этап 3 (S3-T13..S3-T15), потому что без них нельзя сертифицировать ни один пакет.
- **Пакет II** — L3–L6: реестр клиентов, диспетчер, сторож, сигналы, запись журнала, метрики.
- **Пакет III-a** — L7–L9: правила прозы, грамматика согласия, компилятор пакетов.
- **Пакет III-b** — миграция: `AGENTS.md` → корень + модули, манифест, установщик, объём v2.0.

Каждый пакет замораживается одним коммитом (с разрешения владельца), сертифицируется двумя
независимыми параллельно и начиная со второго раунда — по diff (0049 п.1).
