## 3. Ствол S-001

```
 [Intake] → [Frame+Manifest P-L2-001] → [Triage P-L2-002] → [Dispatch P-L2-006]
      → [Execute P-L2-003] → [Accept P-L2-004] ──PASS──→ [Close: owner]
                                   │FAIL (≤2 на корневую причину)
                                   └──→ [Fix round S-005] ─→ [Accept]
                                   │budget exhausted
                                   └──→ [P-L2-007 audit] ─→ owner
 любой узел ──premise wrong / rule not found──→ P-L0-002
```

Кто закрывает (PROTO-DEC-0057 п.2). Стандартный цикл: после PASS или RECOMMENDATION ревьюера работа
идёт к сертификатору; его PASS одобряет работу от имени сертификатора и закрывает её без владельца;
его FAIL или RECOMMENDATION отправляет работу владельцу. Работа над ядром: после ревьюера — владелец
(PROTO-DEC-0054 п.4). Узел [Close: owner] на схеме относится к работе над ядром.

Правило ствола: переход — по артефакту, а не по выбору агента. Узел считается пройденным, когда
существует его выходной артефакт (L5). Это прямой перенос идеи statecharts (M §4): контекст узла —
путь от корня.

## 4. P-L2-001 Рамка задачи и манифест окружения

Основание. Класс B: провал «Битвы за луну» — ошибка рамки (M §4, «самая опасная»); инцидент agy —
модель разрешений не была известна (M §7). Класс C: шаблон 1 внешнего синтеза E.

**task-frame** (артефакт L5, фиксированные поля):
- `goal` — что считается успехом, проверяемо;
- `non-goals` — что явно вне задачи;
- `sources` — список источников **со сверкой с инвентарём** (R-L0-16): для каждого строка
  `tracked|untracked|missing`;
- `baseline` — полный SHA;
- `scope-id` — id scope в форме `kind:name` из грамматики назначения (CORE-ARCH-3 §4); выпускает
  владелец или координатор, один на рамку; строки `## Roles` и `Orientation:` ссылаются на него;
- `parent-scope` — id родительского scope или `-`; по нему работает слияние строк ролей;
- `scope` — пути, которые можно править (не путать с `scope-id`);
- `forbidden` — запрещённые пути, по умолчанию из PROTOCOL.md плюс пути исчерпанных причин (§6);
- `risk` — класс риска по 0038;
- `tier` — из P-L2-002;
- `success` — критерии приёмки;
- `budgets` — попытки, простой, пробуждения, общий лимит.

**environment-manifest**: инструменты (`TOOL-*`), нужные права клиента, флаги из профиля клиента,
способности (0031). **Правило:** инструмент, которого нет в манифесте, не используется. Заблокированный
инструмент — стоп по P-L0-002, а не обход. Манифест читает диспетчер (L3), чтобы выдать узкие права
(0047 п.7).

## 5. P-L2-004 Приёмка

- **Пакет кандидата** (R-09): `Baseline`, `Candidate`, `Scope-ID`, `Diff` (вычисленный список путей и
  хеш), `Closes-findings` (id, каждый разрешается в ledger, иначе выход 2), `Producer-journal`,
  `Producer-Evidence` (дайджест кандидата, CORE-ARCH-6 §2). Пакет генерирует скрипт и выдаёт
  **одинаковые байты** обоим сертификаторам (X S-codex-04).
- **Diff-сертификация** со второго раунда (0049 п.1). Сертификатор расширяет чтение, если
  изменённый код зависит от неизменённого, и записывает причину.
- **Сквозное чтение** (H-16): сертификатор получает на чтение полный текст инструментов из манифеста
  окружения исполнителя. Использование инструмента вне манифеста — находка.
- Вердикт: только закрытый словарь (0041 п.3); объективное правило блокировки (0041 п.4).

## 7. Сценарии S-003 и S-004 (R-15)

**S-003 исследовательский цикл.** Отдельный документ в L2 (большинство C и D). Граф:
```
 рамка владельца → раунд 1 (одна зона — один владелец) → раунд 2 (вызовы, не своя зона; один синтез)
 → раунд 3 (три синтеза без взаимного чтения; строка независимости в журнале)
 → (b) черновик решения → (c) две независимые критики в форме согласия → (d) итоговый план
 → владелец: принять | изменить | отклонить
```
Нет отчёта — значит «ожидается», а не «согласен» (X S-codex-08). Лимиты отчётов проверяет
диспетчер при передаче (C S-claude-16). `PAIRED-CYCLE.md:160` сужается до циклов реализации
указателем (0052 п.3).

**S-004 правка ядра** = S-003 для замысла + P-L0-001 для каждой записи + S-002 для реализации +
P-L2-004 с двумя независимыми сертификаторами для посадки. Программа CORE-ARCH сама идёт по S-004.
Это её первая проверка на себе.

## 9. P-L2-009 Конвейерное ревью (пилот, H-19)

Запускается только после одобрения владельца (В-7 в CORE-ARCH-1).

Мысль владельца: «сдаёт на ревью, и не факт, что будет ждать. Если есть свободный ревьюер, работает
дальше по той же схеме. После завершения цикла проверяет, нет ли правок».

Правила пилота:
1. **WIP ≤ 2**: у исполнителя не больше двух кандидатов на ревью одновременно.
2. Следующий кандидат явно объявляет базу: `Base: <candidate-1>` (стек).
3. Если ревью кандидата 1 дало FAIL, кандидат 2 перебазируется после исправления; его ревью
   обнуляется только по затронутым путям.
4. Посадка в ядро — строго по порядку стека.
5. Перед стартом нового кандидата исполнитель собирает вердикты («проверяет, нет ли правок»);
   открытый FAIL идёт первым.
6. Два писателя в одном файле исключены: ревьюер не правит.
7. Кандидат на ревью заморожен (исправлено по CB-11). Промпт ревью называет коммит кандидата (полный
   SHA), и ревьюер читает пути из него (`git show <sha>:<path>`); если коммита нет, промпт перечисляет
   SHA-256 каждого проверяемого пути, и ревьюер сверяет их в начале и в конце. Пока ревью идёт,
   исполнитель не правит эти пути; правка после отправки — новый кандидат со своим `Base:` (правило 2),
   о котором ревьюеру сообщают отдельно. Пилот ограничивает число этапов (PROTO-DEC-0062 п.4), а это
   правило — правки под ревью.

Метрики: время простоя исполнителя; число переделок из-за FAIL базы. Критерий отказа: переделки
съедают больше времени, чем сэкономлено на простое, за два этапа подряд.
