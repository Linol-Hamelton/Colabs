## 2. Threat Model Scope & Architectural Boundaries

To ensure objective evaluation, reviewers must evaluate against the agreed-upon threat model and design boundaries:

1. **Lock Token Threat Model**: The lock token is an **anti-accident barrier**, NOT an adversary isolation sandbox (`QUICKSTART.md:62`, `PROTOCOL.md:68-75`, `DEC-0016`). The token is stored in `.ai/runtime/<owner>.json` and is readable by any process with local filesystem read permissions. Its purpose is preventing accidental lock theft by transient CLI commands, child processes, or unrelated scripts, not defending against malicious local OS execution.
2. **PID Affiliation Boundary**: `operate(..., 'acquire')` accepts own PID (`process.pid`), parent process (`ppid`), or a registered supervisor PID accompanied by the matching `--session-token`. System PIDs (`<= 4`) are unconditionally rejected.
3. **Archive Storage Model**: Full deletion or arbitrary manual truncation of `.ai/ARCHIVE.md` on the local disk is outside the runtime threat model (`DEC-0016`). Storage tampering is caught by Git tracking (`git diff`, `git status`) and Merkle parent-hash verification across sessions.
4. **Transitional Root Invariant**: The transitional root marker (`chain root: transitional`) is scoped per chain and per repository history.
