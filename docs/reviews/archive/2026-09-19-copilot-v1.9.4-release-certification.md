## Deep Dives

### Lock token and session spoofing

The lock registration path is coherent and fail-closed. `--session-pid` rejects system PIDs and requires either the current process, parent process, or a registered supervisor PID while matching the nonce-derived token. I also confirmed the runtime state is tied to `owner.json` and the lock file holds only the digest (`tokenHash`), consistent with the anti-accident threat model and the protocol’s local-filesystem boundary.

### Archive cryptographic invariants

The archive verification code enforces graph-level invariants rather than string presence checks alone. The implementation accepts independent chains while rejecting orphaned segments and mis-rooted transitional entries. The second-batch boundary regression is a strong check that the canonicalization fix is durable across later archive append activity.

### Legacy evidence and verification policy

Legacy format receipts are retained as legacy, not silently upgraded. Verification is strict without `--allow-legacy`, and the doctor output correctly surfaces legacy warnings while returning Healthy for the source role. This matches the intention of fail-closed compatibility without silently certifying unauthenticated records.

### Canonical hash helper deduplication

The shared canonical hash helper is the right design choice for avoiding drift between archive and handoff paths. Anchoring the regex to exact field names removes the ambiguous label collision risk described in the previous review phases.

### Completion gate and report persistence

The validator enforces the completion gate for a completed task: the path must be under `docs/reviews/`, non-empty, and separate from the adversarial prompt. The review artifact must identify a reviewer and a PASS or RECOMMENDATION verdict. The repository state here satisfies that requirement once the final certification entry is written and persisted.

## Alternatives Considered & Trade-offs

- **Alternative A**: Keep the older permissive validation rules - **Rejected because**: it increases the chance of silent archive drift and false-positive verification.
- **Alternative B**: Rewrite historical Evidence receipts to format 2 in place - **Rejected because**: it would break provenance, parent-hash continuity, and the signed model of historical verification.
- **Alternative C**: Allow arbitrary live PIDs during lock acquisition - **Rejected because**: it reintroduces lock squatting and DoS conditions under the same accidental-local-CLI threat model.

---

## Recommendations & Actionable Plan

1. Keep the runtime token model as a local anti-accident barrier and document its boundary explicitly for downstream users.
2. Preserve the legacy format warnings as a compatibility signal rather than converting historical receipts silently.
3. Continue to treat the archive graph as a cryptographic chain, not as a set of plain text strings.
4. Preserve the review persistence rule: prompt and report files remain under `docs/reviews/` before any chat summary is emitted.
