### C40-02 — устойчивая база отсчёта

- Новое обязательное поле лёгкого пути в секции `## Completion gate`: `- Baseline: <40-hex sha>`.
- Baseline обязан быть **неизменяемым** идентификатором: ровно 40 шестнадцатеричных символов. `HEAD`, имена веток, теги, короткие sha и любые подвижные ссылки отвергаются до вызова git (regex `^[0-9a-f]{40}$`), иначе strict path.
- Проверки: `git rev-parse --verify <sha>^{commit}` и `git merge-base --is-ancestor <sha> HEAD`. Набор изменений равен `git diff --name-only <sha>` плюс untracked.
- Отсутствующий, неразрешимый, неполный, не являющийся предком baseline, сбой git, пустой набор — strict path. Пустой diff **не** лечится разрешением.
- Baseline фиксируется **до** начала реализации и записывается в dispatch задачи. Ревьюер отдельно подтверждает, что он покрывает всю работу задачи: цитирование произвольного sha этого само по себе не доказывает. Это требование входит в документируемый контракт вместе с полями `Scope` и `Baseline`.
- Обновите все семь существующих light-path тестов: `tests/gate.test.cjs:455,470` и `tests/validator.test.cjs:268,282,311,324,338`.
- Wave C сама лёгкий путь не использует: она меняет `.ai/**`, `validate-protocol.ps1` и `tests/**`, то есть идёт strict path с полной парой prompt+report. Поле `Baseline` здесь реализуется и тестируется, а не применяется для сертификации этой волны.

## Порядок закрытия

Дайджест дерева исключает `.ai/worklog` (`protocol-handoff.cjs:404`), поэтому несколько владельцев могут записать receipt на одном дереве. Всё остальное в дайджест входит, отсюда порядок:

1. Gemini реализует код, тесты, документацию.
2. Gemini публикует unified adversarial prompt под `docs/reviews/` (не более 150 строк).
3. **Gemini записывает промежуточный receipt** (`record --owner <gemini-owner>`). Это контроль передачи, а не финальный результат.
4. **DeepSeek проверяет его `verify --owner <gemini-owner> --deep` ДО любых своих изменений.** Провал проверки возвращает работу на шаг 1; своих правок DeepSeek при этом не вносит. Требование уже записано в `.ai/docs/PAIRED-CYCLE.md:45`.
5. DeepSeek публикует независимый отчёт (не более 250 строк) с `Mode: CERTIFYING` и `Receipt-Owner`.
6. Ограниченное внешнее ре-ревью (Codex или Claude headless) публикует свой отчёт. Если оно требует исправлений — цикл **возвращается на шаг 1**, а не дописывает к старым отчётам; после remediation нужна повторная сертификация.
7. Под локом обновляются `.ai/TASK.md` и `.ai/PLAN.md`. **Это последнее изменение дерева.**
8. Каждый владелец пишет свою запись журнала со всеми пятью метками, цитируя свой путь артефакта.
9. `record --owner <owner>` для всех владельцев; затем `verify --owner <owner> --deep` для всех; затем проверка завершённого состояния (ниже).

В `## Completion gate` задачи цитируется unified prompt Gemini (шаг 2) и **certifying-отчёт DeepSeek** (шаг 5). Внешнее ре-ревью шага 6 гейтом не проверяется: оно фиксируется в acceptance-критериях `.ai/TASK.md` и цитируется в отчёте и журнале, и его PASS обязателен до перевода задачи в Completed. Назовите обе роли явно, чтобы не было двусмысленности, какой отчёт сертифицирует.
Любая правка после шага 7 обнуляет receipts — повторите шаги 7-9, не редактируя старые отчёты.
