# Консолидированный анализ MCP-исследований и план тестирования

**Дата**: 2026-09-20  
**Анализ**: Сводный анализ результатов MCP Stack Council Round 1  
**Статус**: ADVISORY - рекомендации для будущего планирования  
**Режим**: READ-ONLY анализ без модификаций

## Сводный анализ гипотез, выявленных в исследованиях разных моделей

### 1. Наиболее часто повторяющиеся гипотезы о потенциальной эффективности MCP-серверов:

#### A. Native file/search/git operations (Контрольная группа)
- **Роль**: Универсальный контроль и резервный вариант
- **Модальность**: Файловые операции, поиск, Git
- **Заменяемая операция**: Все нативные файловые/поисковые операции
- **Частота запуска**: Всегда (контрольная группа)
- **Ожидаемая выгода**: Базовая линия, O(релевантных файлов)
- **Стоимость**: 0 токенов схемы, 0 накладных расходов
- **Безопасность**: Локальная песочница, Git как истина

#### B. Serena 1.5.3 (минимальный профиль для навигации по символам)
- **Роль**: Навигация по символам в типизированных кодовых базах
- **Модальность**: AST/Символы/Ссылки
- **Заменяемая операция**: `rg symbol` + чтение целых файлов для навигации
- **Частота запуска**: Высокая для задач рефакторинга/навигации
- **Ожидаемая выгода**: Сокращение чтения лишних файлов на 30-50% (в больших проектах)
- **Стоимость**: Неизвестна, зависит от LSP-серверов
- **Безопасность**: Read-only режим, локальный процесс

#### C. Repomix MCP 1.18.0 (песочница для срезов репозитория)
- **Роль**: Генерация компактных срезов контекста
- **Модальность**: Срезы кода/файлов
- **Заменяемая операция**: Последовательные чтения нескольких файлов
- **Частота запуска**: По необходимости для широких аудитов
- **Ожидаемая выгода**: Компактные срезы без выгрузки всех файлов
- **Стоимость**: Неизвестна, время упаковки
- **Безопасность**: Read-only, ограничение по корню репозитория

#### D. Qdrant MCP (векторный поиск по архивам)
- **Роль**: Семантический поиск по истории/документации
- **Модальность**: Векторы/Текст
- **Заменяемая операция**: Линейный поиск по архивам `docs/reviews/archive/`
- **Частота запуска**: Редко, для исторических запросов
- **Ожидаемая выгода**: Семантическое попадание в контекст
- **Стоимость**: Высокая (векторизация, индексация)
- **Безопасность**: Read-only к локальному хранилищу

#### E. Маршрутизатор профилей (ведущая архитектура)
- **Роль**: Активация одного MCP-сервера по классу задачи
- **Модальность**: Все модальности (в зависимости от сервера)
- **Заменяемая операция**: Выбор подходящего инструмента
- **Частота запуска**: По классу задачи
- **Ожидаемая выгода**: Оптимальный баланс затрат и выгоды
- **Стоимость**: Сумма выбранного профиля
- **Безопасность**: Сохраняет нативный fallback

### 2. Наиболее часто повторяющиеся предостережения и риски:

#### Высокие риски:
1. **Аддитивное использование MCP** - модель использует MCP в дополнение к нативным операциям, увеличивая затраты (H1 Arm B: +72.79% токенов)
2. **Превышение бюджета схемы** - превышение лимита в 1,500 токенов (PROTO-DEC-0034)
3. **Отсутствие механизма замены** - MCP добавляется как второй путь, а не заменяет нативные операции
4. **Нарушение авторитетности Git** - создание второго источника истины (например, Kindex)

#### Средние риски:
1. **Отсутствие провенанса** - результаты без хешей контента/пути
2. **Проблемы с обновлением индекса** - несоответствие результатов текущему состоянию
3. **Проблемы совместимости с Windows** - особенно для LSP-серверов
4. **Накладные расходы на запуск** - особенно для LSP-серверов и индексации

#### Низкие риски:
1. **Отсутствие фильтрации по содержимому** в Qdrant (требует внешнего слоя индексации)
2. **Отсутствие read-only проекции** в Kindex (требует кастомного решения)

## Итоговый план тестирования наиболее вероятных гипотез

### Этап 1: Подготовка и корректировка границ тестирования

1. **Подтвердить точную конфигурацию H1**:
   - Arm B действительно был ограничен: `.ai/bin/**`, `validate-protocol.ps1`, `test-protocol.ps1`, `tests/**`
   - Исключены: `TASK`, `PLAN`, `DECISIONS`, логи и история обзоров
   - Результат: ~88k токенов raw digest + нормальное исследование

2. **Измерить реальные размеры схем**:
   - `tools/list` для каждого кандидата в байтах и токенах
   - Влияние на каждый хост (Codex, Claude, Gemini)
   - Проверить соответствие лимиту <=1,500 токенов

3. **Проверить совместимость с Windows/Node/PowerShell**:
   - Serena: доступность `pwsh` для PowerShell поддержки
   - Repomix: ограничения песочницы для абсолютных путей
   - Qdrant: локальный путь и векторизация

### Этап 2: Первичное тестирование кандидатов (Post-Pilot)

Тестирование разрешено только **после** получения результатов продуктовых пилотов в `D:\Block-Puzzle` и `D:\VPN` и **явной директивы владельца**.

#### Кандидат 1: Repomix MCP grep/slice (ведущий кандидат)
**Цель**: Заменить нативные `rg` + последовательные чтения файлов
**Условия**:
- Только один сервер одновременно
- Строгое правило замены: запрет на дублирование чтений
- Измерение схемы: `tools/list` <=1,500 токенов
- Песочница: root-confined, workspace-only

**Тестовый план**:
- Контроль: native `rg` + точечные чтения
- Кандидат: Repomix MCP grep/slice
- Задачи: 5 широких аудитов + 5 узких правок
- Пороги: >=25% снижение токенов на широких задачах, <=+5% на узких
- Остановка: при любом нарушении порога

#### Кандидат 2: Serena минимальный профиль (для больших проектов)
**Цель**: Заменить символическую навигацию через `rg`
**Условия**:
- Только read-only инструменты
- Только фиксированный набор инструментов
- Только для задач, где навигация по символам действительно нужна
- Проверка провенанса (путь + хеш содержимого)

**Тестовый план**:
- Контроль: native `rg symbol` + чтение файлов
- Кандидат: Serena с фиксированным read-only профилем
- Задачи: 5 задач навигации по символам в `D:\Block-Puzzle`
- Пороги: >=25% снижение токенов на задачах навигации
- Остановка: при превышении схемы или регрессии

### Этап 3: Архитектурные проверки

#### Роутинговая архитектура (ведущая гипотеза)
**Гипотеза**: Ноль MCP по умолчанию, один сервер по классу задачи через роутер
**Преимущества**:
- Минимизация накладных расходов
- Сохранение нативного fallback
- Строгое ограничение количества активных серверов

**Проверка**:
- Необходимо подтверждение на продуктовых пилотах сначала
- Требует разработки логики роутинга
- Требует проверки точности классификации задач

### Этап 4: Безопасность и аудит

#### Проверка провенанса
**Требования для всех MCP-результатов**:
- Путь к источнику
- Хеш содержимого (SHA-256)
- Соответствие текущему Git HEAD
- Недопустимость включения в Evidence или гейты

#### Защита источника истины
**Правила**:
- Git/DECISIONS остаются единственным авторитетом
- MCP-вывод помечается как advisory
- Запрет на создание второго источника истины
- Сохранение graceful fallback на native операции

## Рекомендации по реализации

### Немедленные действия:
1. **Сохранить текущую заморозку** (PROTO-DEC-0036 и PROTO-DEC-0039)
2. **Завершить аудит-закрытие** и очистку корпуса/журналов
3. **Выполнить продуктовые пилоты** в `D:\Block-Puzzle` и `D:\VPN`
4. **Оценить результаты пилотов** на предмет необходимости MCP

### Условия для будущего MCP-исследования:
1. **Явная директива владельца** с датой
2. **Добавление owner-directive в REGISTRY**
3. **Новое принятое решение**, отменяющее или изменяющее PROTO-DEC-0036
4. **Тестирование одного кандидата за раз** (не стека)
5. **Строгие пороги**: <=1,500 токенов схемы, >=25% выгода, <=+5% регрессия

### Архитектурные принципы:
1. **Замена, а не добавление**: MCP должен заменять нативные операции, не добавляться поверх них
2. **Ноль по умолчанию**: по умолчанию MCP не используется
3. **Один сервер одновременно**: максимум один активный MCP-сервер
4. **Раздельный провенанс**: каждый результат должен иметь источник и хеш
5. **Резервный план**: всегда должна быть возможность fallback на native операции

## Заключение

На основе всех исследований, наиболее перспективной гипотезой является **маршрутизируемая архитектура с одним MCP-сервером по классу задачи**, но только **после** подтверждения необходимости в продуктовых пилотах. 

Текущий Colabs не является подходящей площадкой для доказательства эффективности MCP-инструментов, так как это маленький, ориентированный на текст репозиторий, где ценность код-навигации минимальна. Основная ценность MCP-инструментов ожидается в крупных типизированных проектах типа `D:\Block-Puzzle` и `D:\VPN`.

Ключевым инсайтом является то, что **качество замены нативных операций важнее, чем количество доступных инструментов**. Любой MCP-кандидат должен строго заменять нативные операции, а не добавляться к ним, иначе будет повторен сценарий H1 с +72.79% токенов.
